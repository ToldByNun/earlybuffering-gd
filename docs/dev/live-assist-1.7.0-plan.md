# EarlyBuffer 1.7.0 implementation plan and acceptance checklist

Target GD 2.2081. Start from the v1.6.2 ship tree at `aa1f06a`. AP01–AP07 repair and optimize Live as a standalone mode. Run their acceptance tests with an empty learning profile. AP08–AP09 then replace the old assist modes and implement learned Hybrid on top of the accepted Live planner. AP10 closes the release. All boxes below are implementation work.

## What the recordings actually show

Sources are the four local `research_20261115_<time>` directories under the EarlyBuffer research directory. Read the manifest, session, configuration and report together. All four used Live v1, ShadowPlayer, an eight-tick input window, Adaptive on, 12 screen ticks, verify quantum 10, reserve 10%, a 4,003 µs simulation budget and 3,017 tick budget. Orb assist was on and Auto Tune was off. The two FOREST sessions share the same level revision but cover different gameplay. Three packs used StartPos, Zodiac used a normal start. None used practice.

To reproduce, flatten every retained attempt's events from each session. Count `pressObserved` for edges (including releases). For decisions, filter to `kind == planFinished`, group by `assistReason`, and count `adaptiveFellThrough` and `reusedCandidateCount > 0` once per plan. Sort `planUs` and take nearest-rank quantiles. All 59 delay arms had corresponding fire events by pack count. Release and early-attempt gates explain the difference between edges and finished plans. Delay rate alone would reward unnecessary interventions.

* **Start with search scheduling.** Of 180 plans, 179 fell through from Adaptive, seven reused candidates, 176 set `budgetHit`, and 92 returned `pass-budget`. Even successful delays can hit the wall. Median Adaptive work per pack was 1.07–1.09 ms and median classic search was 2.94–3.00 ms. At 240 frames/s a whole frame lasts 4.17 ms. These are planner timings during recording. They identify a plausible hitch mechanism without measuring the user's display frame time or proving how much recording costs.
* **Orb-only Cube is the first reproducer.** 38/39 plans set `usedOrbWindow`, including all 24 budget passes and all 11 immediate-safe passes. Detection alone cannot fix this section. Attempt 14, tick 42, plan 157 had a lethal delay-zero run at tick 93, delays 1/2 screened for 12 ticks, delay 3 alive after 60 and delays 4–8 skipped. That is an unfinished comparison. Attempt 20 also passed budget at ticks 39 and 123. Its approximate evaluator lists planned delay 0 and best surviving delay 3. Attempt 23 closed with a simulated caused classification in the pack report. Preserve favorable and unfavorable examples.
* **Ball deserves an independent experiment.** All 35 plans in 012700 were Ball. Nineteen used an orb window, producing six threat delays, five immediate-safe passes and eight budget passes. Inspect actual activation and landing on each input. The reason label alone cannot identify the player's intended action. The Ball landing path cannot directly explain the 39 Cube decisions in the other FOREST segment.
* **Protect working assists.** Zodiac and Firework already supplied 47 orb delays between them. In Firework, 26 of the 33 budget passes used an orb window. In Zodiac, the five evaluated deaths list planned delay 1 and best surviving delay 8. Check the objective, actual activation and the timing of the next physical click before treating 8 as a better answer.
* **Evidence limits.** The reports use approximate player-only postmortems. Reported simulated prevented/caused counts are respectively 0/0, 0/0, 3/1 and 6/1. A death ending an attempt is a poor label for an earlier click. Neither isolated-ring counts nor the counterfactual effect of changing a decision can be recovered from the reason string. The four packs justify starting now. Collect matched Adaptive-off data during validation if a scheduling difference remains unexplained.

## AP06 — Per-level settings

- [ ] Add per-mode **Orb Chain Verify** with inherited default Auto, explicit On and Off. Auto enables continuation work for a plausible fresh second ring. On requests verification for eligible chains within budget. Off disables only that extra simulation. Global orb assist off takes precedence. Isolated-ring behavior must be identical under all three settings.
- [ ] Add **Modes → Ball → Ground Check** as an inherited per-level policy. Default Auto compares landing and orb intent as in AP04. On keeps ground-priority evaluation for levels that need it. Off skips the optional landing search and retains ordinary collision/survival checks. A disabled Ball mode must still pass inputs untouched.
- [ ] Reuse current config resolution. Document and test global defaults, per-mode defaults and explicit per-level overrides in that order. Round-trip through desktop, in-level settings, local save and imported/cloud config. Old configs with absent keys get Auto. Include effective policies in the fingerprint. Verify level switching restores inherited defaults and that config changes invalidate incompatible learned evidence.

## AP09 — Implement and validate learned Hybrid

- [ ] Start with `EbLevelProfile`, `EbAssistLearning` and `EbSpotTrustMap`. Existing level/mode/X buckets, 17-bin timing histograms and parity distrust supply reusable plumbing. X alone aliases loops and diverging routes. Key samples by level revision, local route/position, mode, player, relevant speed/gravity, edge and recent physical click interval/hold pattern. Include policy/physics compatibility. Bound bucket count and history; evict stale weak evidence first.
- [ ] With Auto Tune on, observe each real edge once, including immediate passes. Record context, proposed/actual delay and phase, baseline versus chosen evidence, local survival, activation or landing, and the next physical input/death. Keep unrelated later deaths, canceled inputs and uncertain counterfactuals separate. Credit a verified rescue more than simple survival; penalize a verified harmful change, reduce confidence after drift, and keep unknown outcomes at zero reward. Maintain action-specific sample counts and decayed reward/weight per delay. Cap weight per attempt so grinding one repeated input cannot overwhelm independent evidence.
- [ ] Cold or conflicting contexts use Live. After repeated independent, consistent outcomes, try the best-supported delay and immediate baseline first, with a short bounded verification of current geometry and the same Live safety contract. Fall back to the remaining Live search on disagreement, missed ring, stale state, unexpected next input or low confidence, using the same frame budget. No autonomous clicks. Proposed Auto Tune off behavior for Hybrid is ordinary Live planning with profile reads/writes disabled; preserve the profile for later re-enable. Keep Live independently selectable and test its existing Auto Tune behavior separately.
- [ ] In Learn show whether samples are accumulating, sufficient for a learned proposal, or rejected by parity. Provide reset-current-level and test persistence across restart, corruption, partial save, version mismatch and edits. Save atomically outside the input hook, without planner threads. Scope learning to the level revision and handle checkpoints and alternate paths without leaking outcomes across attempts.
- [ ] Train on earlier attempts only, freeze the profile, and evaluate on later withheld attempts. Compare cold Hybrid, warm Hybrid, Auto Tune off and accepted Live with identical input streams. Measure verified recovery, harmful interventions, coverage, fallback fraction, ticks/plan, hook p95 and frame p99. Proposed warm gate: ≥20% fewer simulation ticks and lower measured p95 than Live on repeated sections, higher verified recovery on the pooled learned opportunities, and zero new verified harms or lost required control cases. A faster mode that silently passes more recoverable clicks fails. Verify cold/out-of-distribution parity with Live and latency under repeated fallback.
